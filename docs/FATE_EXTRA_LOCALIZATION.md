# Fate/EXTRA 文本校对工作流

本分支在 LinguaGacha 的翻译项目模型上增加了 Fate/EXTRA 专用校对层、文本安全分类、PSP 显示预览和导出 QA。它只处理翻译文本与字库素材，不负责构筑 ISO。

## 三层文本模型

每条文本保存三个彼此独立的字段：

1. **日文原文**：项目条目的 `src`，只读，禁止被翻译或校对操作覆盖。
2. **Lingua 初翻**：项目条目的 `dst`，由 Lingua 翻译流程写入。重新机翻只更新这一层。
3. **最终校对稿**：Fate/EXTRA 元数据中的 `proofread_translation`，由人工校对界面独立保存。

预览和最终文本导出采用以下优先级：

```text
非空最终校对稿 > 非空 Lingua 初翻 > 日文原文
```

因此，重新执行初翻不会覆盖已经保存的校对稿；清空校对稿后会自动回退到最新初翻。

## GUI

Fate/EXTRA 校对页面固定显示三个独立文本框：

- 日文原文（只读）
- Lingua 初翻（只读）
- 最终校对稿（可编辑）

页面还显示文本安全类别、分类置信度、原槽容量、当前编码字节数、分类原因与给译者的限制说明。可以按七类安全类型筛选。

独立“校对”页与“PSP 画面预览”页在侧栏并存：校对页负责跨条目搜索、筛选、排序和集中检查，PSP 预览页负责三层文本、实机布局与安全信息。PSP 预览页监听项目翻译提交事件；Lingua 写入新的初翻后，“Lingua 初翻”文本框按提交批次自动刷新，两页共享后端校对事实但不互相替代。

## 六分支补漏

FE 适配扫描要求用户同时选择：

- 六份带索引日文分支文本所在目录
- `Fate_Extra_JP_完整文本汇总.txt` 完整日文主库
- FE 文本安全分类数据库

初翻目录同时支持六份“带索引初翻”和旧版“无索引译文”。带索引文件按“分支签名 + filepath + char”精确导入，优先级高于旧工程迁移和无索引结构匹配；无索引文件只补充未被带索引文件命中的条目。重复索引存在不同译文时必须报告并留空，不得静默选择。

补漏以完整日文主库为唯一原文权威。工具按 `filepath + char` 比较六分支与完整主库：

- 六分支已存在且原文一致：保留在原分支文件中。
- 完整主库存在而六分支全部缺失：加入虚拟文件 `FE_补漏.txt`。
- 索引相同但原文不同：作为结构冲突报告，不允许静默覆盖。
- 安全分类库缺少记录：条目仍进入补漏，但保守标记为“未解析候选”，翻译和校对可继续，自动注入必须阻断。

补漏条目的日文原文和 Lingua 初翻初始都填入完整主库的日文，最终校对稿留空。安全分类数据库只提供注入安全元数据，不再作为补漏原文来源，也不再使用“仅限六分支已涉及资源路径”或 `display_opcode` 过滤补漏。

显示模式可逐条设为：

- 自动
- 角色对白框
- 全屏文本
- 诗文

角色对白框使用已经确认的 `22 / 21 / 21` 三行规则；控制符不计入显示字符数，实际显示的标点符号计数。全屏文本和诗文使用独立的集中式配置，不套用对白框规则。布局配置位于 `src/shared/fate-extra/fate-extra-layout.ts`，后续可以继续修订，不需要改写 GUI。

## 安全分类与 QA

工具读取 Fate/EXTRA 文本安全分类数据库，并为每条文本保留：

- 分类、置信度与分类依据
- 原始字节数和槽容量
- 指针/重定位信息
- 共享组信息
- 给译者的限制说明

QA 使用 Fate/EXTRA 字形编码映射计算实际编码字节数，不再用 UTF-8 长度代替 PSP 数据长度。检查项目包括：

- 文本结构和定位信息
- Ruby 控制码数量
- 已识别控制码的完整顺序
- 对白框/全屏/诗文的场景化溢出
- 原槽容量与编码字节数
- 未解析候选及其他安全阻断项

导出时同时生成 `fate-extra-injection-safety.json`。该清单供后续注入器读取；存在阻断项时，注入器应阻止对应条目，而不是靠文本编辑器猜测是否安全。

## 翻译提示词

送入模型的内容包含当前条目的安全分类和长度限制，但不要求模型输出这些元数据。Fate/EXTRA 专用提示词还规定：

- 保持控制符和 Ruby 结构及顺序
- `#RUBS` 到 `#RUBE` 之间的日文读音原样保留
- 正文采用 Fate 系列术语和角色语气
- Master 译为“御主”，Servant 译为“从者”
- 尼禄的“余／奏者／汝”按语境处理
- 无意义乱码和损坏文本保持原样

## 路径规则

所有 Fate/EXTRA 输入、输出路径都由用户通过文件或目录选择器指定，不写死盘符。字库任务描述文件临时创建在用户选择的输出目录中，任务结束后清理，不写入系统用户数据目录。

## Windows 发布

本分支提供两套构建配置：

- `electron-builder.json5`：上游完整发布，包含 Go 编写的 CLI 启动器和自动更新器，需要 Go 工具链。
- `electron-builder-gui-only.json5`：Fate/EXTRA GUI-only 发布，不包含 CLI 和自动更新器，不需要 Go；三层文本、QA、预览、字库和导出功能不受影响。

GUI-only 构建命令：

```powershell
npx electron-builder --config buildtools/builder/electron-builder-gui-only.json5
```

## 字库边界

当前仓库内置的旧字库构建器仍以 19 页资源格式为基线。项目外已经验证的双层字库是 23 页、5687 个已映射字符、5888 总容量；两者资源协议尚未统一。

在增加明确的 23 页 `font.txb`、`kanzi.bin` 和高清纹理输出适配器之前，不得把旧构建器生成结果标记为“23 页双层字库”。这一限制不影响三层文本编辑、QA 或安全清单导出。

## 扩展点

后续规则应优先通过以下集中位置扩展：

- 显示规则：`src/shared/fate-extra/fate-extra-layout.ts`
- 元数据字段：`src/shared/fate-extra/fate-extra-types.ts`
- QA/导出清单：`src/backend/toolbox/fate-extra-service.ts`
- 字库与编码：`src/backend/toolbox/fate-extra-font-service.ts`
- 翻译规则：`resource/fate-extra/rules/translation-prompt.md`

不要把路径、场景判断、字库页数或安全阈值散落写死在 React 组件中。

## 精简翻译工程

FE 适配页可从完整工程生成新的独立 `.lg` 精简工程。源工程不会被覆盖：

- `items` 仅保留按原文完整字节严格去重后的有效文本；不执行 trim、Unicode 归一化或控制符清理。
- `fate_extra_compact_source` 保存 SHA-256、完整原文、代表索引、出现次数与冲突标记；哈希命中仍必须核对完整原文。
- `fate_extra_compact_occurrence` 保存全部物理位置、文件顺序、结构行、显示模式与安全分类摘要。
- PSP 预览选中分支文件时，必须从物理位置表按 `row_number + original_item_id` 投影完整路线；去重代表项只负责共享译文，不负责路线排序或文件归属。
- `fate_extra_compact_override` 为后续按单个物理位置覆盖译文预留，不改变组级翻译。
- 明确乱码只从翻译列表排除，原文和位置仍保存在映射中，导出时原样恢复。
- 导出使用分页展开，不把约九十四万条映射一次性加载到 renderer 或 V8；安全分类按物理位置重新读取。

当前实测基线：941,489 个物理位置、28,453 个精确原文组、28,433 个可编辑有效组、20 个明确乱码组。

精简 schema v2 的代表条目按以下顺序选择，禁止再使用单纯的最小 ID：

1. 非空最终校对稿
2. 非空且不同于日文原文的 Lingua 初翻
3. 补漏条目的日文原文副本
4. 空白条目

每个物理位置同时保留原初翻、原校对稿和原状态。全量审计必须证明：物理位置数量、原文、定位、结构 JSON、原译文和状态全部一致；正常文本中任意非空初翻组必须在精简 `items` 中存在。20 个明确乱码组可以不进入普通编辑列表，但其完整物理记录必须保留。

PSP 预览中的显示类型采用即时保存。只改变“自动/对白/全屏/诗文”不得把条目标记为已翻译，也不得持续锁定筛选、上一条、下一条或跳转。右侧三层文本区拥有独立纵向滚动。初翻和校对稿分别与日文原文比较颜色、Ruby及其他控制符序列；序列不同必须显示阻断提示，不能用错误颜色冒充实机效果。
